# Minimalism Rules — 最小化决策阶梯

> 借鉴 ponytail（DietrichGebert/ponytail）的工程纪律：**最好的代码是没写出来的代码。**
> 本规则把"最小改动"从原则变成 Agent 可逐级执行的决策过程。

## 摘要（注入用）

- 写代码前爬 7 级阶梯：YAGNI → 复用代码库 → 标准库 → 平台原生 → 已装依赖 → 一行 → 最小可行。
- 先读任务和调用链，再爬阶梯；改错位置的小 diff 不是懒，是第二个 bug。
- Bug 修根因：grep 所有调用方，修在共享路径上。
- 绝不简化：信任边界校验、防数据丢失、安全、无障碍、用户明确要求的东西。
- 有意简化必须 `agency: <上限>, <升级路径>`；非平凡逻辑留一个可运行检查。

## 1. 决策阶梯（写代码前，从第 1 级开始，停在你站得住的那一级）

```text
1. 这个真的需要存在吗？         不需要 → 跳过并说明（YAGNI）
2. 代码库里已经有了吗？         复用已有 helper / util / 模式，不重写
3. 标准库能做吗？               用它
4. 平台原生能力覆盖吗？         <input type="date"> 优于日期选择器库；CSS 优于 JS；数据库约束优于应用代码
5. 已安装的依赖能解决吗？       用它；绝不为了几行代码引入新依赖
6. 能一行搞定吗？               就一行
7. 只有以上都不行：写最小可行实现
```

**阶梯在理解问题之后运行，而不是代替理解**：先读任务和它触及的代码，端到端追踪真实调用链，再爬阶梯。两步都成立时取更高级并继续。最小的但改错位置的改动不是懒，是第二个 bug。

## 2. Bug 修复 = 修根因，不修症状

报告描述的是症状。动手前 grep 这个函数的所有调用方：在共享函数里加一道防护，diff 比在每个调用方各加一道小——而且只修工单指出的路径会让兄弟调用方继续坏着。**修一次，修在所有人流经的地方。**

## 3. 规则

- 不建没被要求建的抽象：一个实现的接口、一个产品的工厂、永不变化的配置，都是过度设计。
- 不加没人要的样板代码，不为"以后"搭脚手架——以后自己能搭。
- 删除优先于新增；无聊优先于聪明（聪明是凌晨三点解码的东西）。
- 文件尽可能少；最短可用 diff 胜出——但只在你理解问题之后。
- 复杂请求：交付懒版本并在同一回复里质疑："已做 X；Y 覆盖了它。需要完整 X 就说。"绝不因为可以默认答案而卡住。
- 两个标准库方案同大小：选边界情形正确的那一个。懒 = 少写代码，不是选更脆弱的算法。

## 4. 绝不偷懒清单

永远不简化掉：信任边界的输入校验、防止数据丢失的错误处理、安全措施、无障碍基础、用户明确要求的东西。用户坚持要完整版 → 照做，不再争论。

**硬件不是纸面理想**：真实时钟会漂、真实传感器有偏差——留校准旋钮，不只是少写代码。

## 5. 简化必须留痕

有意切掉一个真实角、且知道有上限的简化（全局锁、O(n²) 扫描、朴素启发式），必须用 `agency:` 注释标注上限和升级路径：

```text
# agency: 全局锁，吞吐成为瓶颈时改按账号分锁
# agency: O(n²) 扫描，规则库超 1 万条时改索引方案
```

`agency debt` 命令把这类注释收割成债务台账，防"以后再说"变成"永远不做"。

## 6. 非平凡逻辑必须留一个可运行的检查

带分支、循环、解析、金钱/安全路径的逻辑，完成后必须留**一个**最小可运行检查——逻辑坏了它就会失败（assert 自检或一个很小的测试文件；不引入框架、不加 fixture）。一行能写完的平凡改动不需要测试（YAGNI 同样适用于测试）。

## 7. 输出纪律

代码优先；随后最多三行：跳过了什么、什么时候加回来。解释比代码长 → 删解释——每段为简化辩护的文字都是悄悄混回来的复杂度。用户明确要的报告/讲解不在此列，完整给出。
