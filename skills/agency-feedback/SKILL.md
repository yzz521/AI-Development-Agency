# Skill: agency-feedback — 自动反馈采集与提案

## 自动触发（任务收尾必做一次内部检查）

任何完成了分析、设计、编码、Review、排障或文档任务的 Agent，在最终回复前都必须快速检查：

1. 是否遇到没有规则覆盖的情况（rule_gap）？
2. 是否发现规则过时、与项目事实/当前技术版本冲突（rule_stale）？
3. 是否存在规则但本次执行未遵守，或规则表述导致歧义（rule_violated）？
4. 是否缺少、不适用或顺序不合理的 Workflow（workflow_gap）？
5. 是否缺少或过时的项目/技术背景（context_gap）？

只记录本次任务中真实观察到的问题。没有问题就不记录，不写 rule_applied 凑数。

## 自动记录（由 Agent 执行，不让用户手动操作）

发现问题时，Agent 应直接调用已安装的 Agency CLI：

```bash
agency feedback --kind <合法类型> --detail "<可核查现象>" \
  --project "<项目名>" --task "<本次任务>" \
  [--agent "<实际使用的 Agent>"] [--rule "<实际相关规则路径>"]
```

- 先检查 `agency` 命令是否可用；若不可用，使用规范库中的 `scripts/feedback.sh`，或报告未能落盘的原因。
- 不要让用户复制命令，也不要只在最终回复中口头提及问题。
- `--detail` 写观察事实：触发条件、实际表现、缺失/冲突点；不写“规则不好”等主观判断。
- 只填写本次真实使用的项目、Agent、任务和规则；不确定的字段省略。
- 同一问题在同一任务中只记录一次；不要为一个根因拆成多条重复反馈。
- 若任务运行环境无法写入中央仓库，明确告知用户反馈未落盘，并给出可复制的记录内容；不得声称已记录。

## 何时创建提案

Agent 不应在每次发现问题后自动修改规则：

- 单条反馈：先记录，等待累积。
- 同类问题反复出现（默认 3 条）或属于高风险规则过时/安全问题：自动整理提案草稿。
- 提案必须引用真实反馈文件和任务证据；证据不足时只列为候选，不创建正式提案。
- 创建提案使用 `agency propose`，不直接改 `rules/`。
- 非破坏性提案进入 PR；删除规则、改变强制行为或 MAJOR 变更必须等待人工批准。

## 边界

- 不因任务成功就写反馈；不虚构证据。
- 不直接修改规则文件，不自动合并 PR。
- 业务项目专属约束写回业务项目，不污染中央 Agency。
- 规则已被遵守但用户明确表示不满意时，记录真实的 rule_violated 或 rule_gap，并说明观察到的行为，不推断用户意图。

## 退出

若记录了反馈，最终汇报反馈文件路径；若未发现问题，不必专门向用户汇报“没有反馈”。
