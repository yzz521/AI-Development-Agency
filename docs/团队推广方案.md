# AI Development Agency 团队推广方案（待审）

> 状态：草案，待评审
> 目标：公司内部开发默认遵守本规范库的规范与边界，**不依赖每次手写提示词**
> 前置约束：团队工具不统一（Cursor / Claude Code / Codex / 网页端混用）

---

## 一、问题定义

当前规范库是**为单机个人设计**的，有两个结构性问题挡住团队化。

### 1. 规范到不了同事手上

项目通过 `.ai/agency` 软链接接入中央规范库，而 `.ai/` 在业务仓库里是 gitignore 的（Javert `.gitignore:132`）。同事 clone 业务仓库后**拿不到任何规范入口**，要能用得完成四步：

1. clone `AI-Development-Agency`
2. 放到与业务仓库精确匹配的相对目录位置
3. 装 CLI 到 PATH
4. 每个项目跑一次 `agency init`

每人每项目一遍，且依赖目录结构与作者一致。这也解释了为什么 `init-project.sh` 的相对路径 bug 能影响 30 个项目而长期无人发现（v1.4.1 已修）——**从来没有第二个人验证过接入**。

### 2. 自动注入不等于遵守

Javert 的编码规范写在 `CLAUDE.md` 里并标注「已强制」，而 `CLAUDE.md` 是每次对话无条件注入 AI 上下文的。实测存量违反情况：

| 规范条目 | 存量违反 |
|---|---|
| 业务 API 一律 POST | 3 个文件有非 POST 映射 |
| 禁止 `@PathVariable` 传业务参数 | 1 个文件 |
| 禁止 `Map<String, Object>` 作业务参数 | 57 个文件 |
| 禁止行内全限定类名 | 23 个文件 |
| `@RequestBody` 必须 `@Valid` | 20 个文件 |
| 机构代码统一 `yljgyqdm` | 2 个生产文件仍用旧名 `ylzzjgdm` |
| SQL 禁 `LIMIT` / 禁反引号 | 0 ✅ |

典型样本：

- `ReportController.java:65` 返回 `ApiResponse<Map<String, Object>>` —— 同时违反「禁 Map 作业务参数」与「VO 必须类型化」
- `ResAppTaskDetailVO.java:16` 一行内违反三条：VO 用 Map、Map 作业务字段、行内全限定类名
- `DrgDipEngineAdapter.java:52` 写 `java.util.List<com.javert.engine.model.UnifiedFinding>`
- `CLAUDE.md` 声称 `ylzzjgdm` 「已全部重命名」，实际 `OcrTpIngestionService.java` 与 `ThirdPartyApiClient.java` 仍在使用

**结论：规范已经在 AI 上下文里，仍被违反。** 只做到「自动注入」，效果与现状相同。要真正约束，必须有一层不依赖 AI 自觉的机器门禁。

## 二、机制覆盖矩阵

工具不统一是本方案最强的约束条件，它否掉了任何依赖单一工具的方案。

| 机制 | Cursor | Claude Code | Codex | 网页端 | 手写代码不用 AI |
|---|---|---|---|---|---|
| 根目录 `AGENTS.md` | ✅ 自动 | ⚠️ 待实测 | ✅ 自动 | ❌ | ❌ |
| 根目录 `CLAUDE.md` | ✅ 自动（无条件） | ✅ 自动 | ❌ | ❌ | ❌ |
| `.cursor/rules/*.mdc` | ✅ 按 globs 条件加载 | ❌ | ❌ | ❌ | ❌ |
| `.cursor/skills/`、`.cursor/agents/` | ✅ 自动发现 | ❌ | ❌ | ❌ | ❌ |
| `.ai/agency/`（现状） | ❌ 非发现目录 | ❌ | ❌ | ❌ | ❌ |
| git `pre-commit` hook | ✅ | ✅ | ✅ | ⚠️ 绕不过提交 | ✅ |
| CI（PR 门禁） | ✅ | ✅ | ✅ | ✅ | ✅ |

两个要点：

- **`.ai/agency/` 不是任何工具的自动发现目录。** Cursor 自动发现的是 `.cursor/`、`.agents/`、以及兼容的 `.claude/`、`.codex/`。项目 `AGENTS.md` 里写的 `.ai/agency/agents/...` 路径目前只是文本提示，没有注入保证。
- **只有 CI 覆盖全部情况。** 这是唯一与工具无关、且对不用 AI 的人也生效的一层。

## 三、三层架构

### 第一层 · 自动注入（零配置，跨工具）

由规范库**生成** `AGENTS.md` 并**提交进每个业务仓库**。clone 即生效，无需装 CLI、无需软链接。

- 内容：项目简介 + 技术栈 + 红线规范 + 常用命令 + Agent 路由
- 生成而非手写，避免各仓库副本漂移
- `CLAUDE.md` 与 `AGENTS.md` 内容重叠会导致**双份注入**，需去重：建议 `CLAUDE.md` 做成指向 `AGENTS.md` 的软链接（git 可存软链接），或由生成器同时产出并在 CI 校验一致性

**这一层的作用是降低违规概率，不是强制。**

### 第二层 · 条件加载（仅 Cursor 用户受益）

`.cursor/rules/*.mdc` 按 `globs` 触发：改 `.java` 才加载 Java 规则，改 SQL 才加载方言规则。同样提交进仓库。

- 扩展名必须 `.mdc`，放 `.md` 会被静默忽略
- frontmatter 仅支持 `description` / `globs` / `alwaysApply`
- 官方建议单规则 500 行以内，拆成可组合小规则

**这一层解决「规范太长塞不进上下文」，属增益项，不是团队一致性的依赖项。**

### 第三层 · 机器门禁（真正的强制）

`agency check` 已实现（v1.6.0）。业务仓库执行 `agency check --install` 即可挂上。默认只开 `java-map-object` / `sql-select-star` / `secret-hardcoded`，只卡增量。

可机检的规则（已验证存量基线；**中央默认 on 只有前三相关的低误报项**）：

| 规则 | 检查方式 | 存量 |
|---|---|---|
| 业务 API 一律 POST | 扫 controller 层非 POST 映射注解 | 3 |
| 禁 `@PathVariable` | 扫注解 | 1 |
| 禁 `Map<String, Object>` 作业务参数 | 扫 controller/service 签名与 VO 字段 | 57 |
| 禁行内全限定类名 | 扫 `java.*.Class`，**必须排除 import 行** | 23 |
| `@RequestBody` 必须 `@Valid` | 扫注解相邻性 | 20 |
| SQL 禁 `LIMIT` | 扫 mapper/xml | 0 |
| SQL 禁反引号 | 扫 mapper/xml | 0 |
| 机构代码禁旧名 `ylzzjgdm` | 扫标识符 | 2 |
| OCR 日志禁记敏感字段 | 扫 `log.*` 参数中的敏感字段名 | 待定 |

需人工评审、不做机检的（避免误报）：魔法值、Controller 是否拆包 DTO、VO 是否语义合理、医疗业务口径。

中央默认 **on**：禁 `Map<String, Object>`、禁 `SELECT *`、禁明文密钥。其余上表项默认 **off**（含 PathVariable、FQCN、RequestBody+Valid、LIMIT/反引号、敏感日志）。一律 POST、`ylzzjgdm` 是 Javert 专有，**不要**写进中央 catalog。

## 四、两个必须遵守的落地原则

### 1. 门禁只卡增量，不卡存量

存量共 106 处文件级命中。若一次性全量启用，团队第一天就会关掉 hook。

- 门禁对 **diff** 检查，不对全仓库
- 存量进债务台账（`agency debt`），按模块分批清理
- 每条规则单独开关，逐条启用

### 2. 上线前必须实测误报率

本方案起草过程中的真实教训：第一版「禁全限定类名」正则报出 **417 个文件**，核实后发现绝大多数是 `import java.util.List;` 这类**合法 import**，真实违规仅 **23 个** —— 误报 18 倍。

**误报是门禁的头号杀手。** 每条规则启用前必须：

1. 在存量代码上跑一遍
2. 人工抽样确认命中是否真违规
3. 误报率不为零则先修正则，不得上线

## 六、明确不做

- **不为每个工具维护一套 Agent Prompt** —— 规范库是唯一真相，工具侧只做适配
- **不靠软链接分发到业务仓库** —— 换机器、换目录结构就断，且被 gitignore
- **不指望 AI 自觉替代门禁** —— Cursor 官方文档亦明示「AI guidance should not be your only security control」
- **不做全量存量整改** —— 按债务台账分批，不阻塞交付
